# HW4 — промежуточное представление и базовые оптимизации

## Запуск

Из корня репозитория:

```bash
go test ./...
go run ./cmd/ir -in examples/hw4_ir.fun \
  -before build/ir-before.txt \
  -out build/ir-after.txt \
  -json build/ir.json \
  -cfg build/cfg \
  -graph build/interference
```

`-in` обязателен. Если `-out` не задан, оптимизированный IR печатается в stdout. Диагностика и метрики печатаются в stderr.

Флаги:

| Флаг | По умолчанию | Назначение |
|---|---:|---|
| `-no-opt` | false | отключить все оптимизации |
| `-const` | true | распространение и свёртка констант |
| `-algebra` | true | алгебраические упрощения |
| `-dce` | true | локальное удаление мёртвых временных |
| `-cse` | false | common subexpression elimination в пределах базового блока |
| `-before FILE` | — | не оптимизированный IR |
| `-out FILE` | stdout | оптимизированный IR |
| `-json FILE` | — | JSON до/после оптимизаций и метрики |
| `-cfg DIR` | — | CFG каждого метода в DOT |
| `-graph DIR` | — | граф конфликтов временных в DOT |

Для запуска без оптимизаций:

```bash
go run ./cmd/ir -in examples/hw4_ir.fun -no-opt
```

Отдельные оптимизации можно отключать, например:

```bash
go run ./cmd/ir -in examples/hw4_ir.fun -const=false -cse=true
```

## Формат IR

IR — трехадресный код. Каждая инструкция хранит opcode и необходимые операнды в отдельных полях. Временные обозначаются `%t1`, `%t2`, ...; метки — `L1`, `L2`, ...; имена исходных переменных сохраняются.

| Инструкция | Значение |
|---|---|
| `%t1 = 12` | `const`: загрузка константы |
| `x = %t1` | `move`: копирование |
| `%t3 = x + %t1` | `bin`: бинарная операция |
| `%t4 = -x` | `unary`: унарная операция |
| `%t5 = array[index]` | `load`: чтение элемента массива |
| `array[index] = value` | `store`: запись элемента массива |
| `%t6 = call f(args)` | `call`: вызов функции с одним результатом |
| `x, y = call f(args)` | `call`: вызов с несколькими результатами |
| `if %t1 != 0 goto L1` | условный переход при ненулевом значении |
| `goto L1` / `L1:` | безусловный переход / метка |
| `return [x, y]` | возврат объявленных результатов функции |

JSON-представление сохраняет те же поля (`op`, `dest`, `dests`, `arg1`, `arg2`, `operator`, `args`, `target`), а также имена параметров, результатов и локальных переменных с типами объявленных параметров/результатов и `uses`. Поэтому backend может работать с IR без разбора текстового дампа.

## Архитектура

- `internal/ir/ir.go` — модель IR и инструкции.
- `generate.go` — AST -> IR.
- `cfg.go` — разбиение на базовые блоки, рёбра управления и обратные рёбра.
- `optimize.go` — локальные оптимизации.
- `liveness.go` — итеративный анализ `IN/OUT` по CFG.
- `interference.go` — граф конфликтов временных по живости.
- `coloring.go` — жадная раскраска в порядке невозрастания степени вершины.
- `print.go` — текстовый IR и DOT.
- `cmd/ir` — конвейер: lexer -> parser -> semantic analysis -> IR -> CFG/optimization/metrics.

## Оптимизации и ограничения

1. Constant propagation/folding: подстановка известных констант внутри базового блока и вычисление константных арифметических/сравнительных/логических операций. Состояние констант сбрасывается на границах блоков, поэтому значения из одной ветви не переносятся в другую.
2. Algebraic simplification: `x + 0`, `x - 0`, `x * 1`, `x / 1`, `0 + x`, `1 * x`, `x * 0`.
3. Local DCE: удаляются неиспользуемые временные значения внутри блока. Записи в исходные переменные не удаляются, поскольку они могут быть использованы в последующих блоках. Вызовы, чтение/запись массивов и управляющие инструкции сохраняются.
4. CSE (опционально): одинаковые бинарные выражения переиспользуются только внутри блока. Таблица сбрасывается при вызовах, операциях с массивами и записи в исходную переменную.

`assert` и `assume` являются конструкциями верификации и на данном этапе не порождают исполняемых инструкций. Формулы и кванторы также не являются частью исполняемого тела функции. У AST нет явного `return`: по завершении тела возвращаются переменные, перечисленные в `Function.Returns`.

Логические условия в текущем IR представлены операциями над булевыми значениями; backend должен трактовать `and`, `or`, `->` как логические операции. Если язык задаёт для них short-circuit-семантику, при lowering в backend необходимо сохранить её.

Анализ живости выполняется по CFG до фиксированной точки. Раскрашиваются именно временные `%tN`; исходные переменные остаются отдельными именованными слотами. Жадная раскраска не гарантирует минимальное число цветов, но даёт допустимое распределение для построенного графа.

## Метрики

CLI выводит для каждой функции:

- число инструкций до/после;
- число встречающихся временных до/после;
- число цветов графа конфликтов оптимизированной функции.

Проверка семантической эквивалентности выполнения до/после требует интерпретатора IR или backend. В текущем HW4 добавлены unit-тесты на lowering, структуру CFG, оптимизации и раскраску; полноценный дифференциальный исполнитель не входит в этот этап.
