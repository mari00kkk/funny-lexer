# HW3 — Semantic Analysis

## 1. Описание задания

Реализован семантический анализатор для языка Funny. Он выполняет проверки программы после синтаксического анализа и помогает обнаруживать ошибки, которые нельзя определить только по структуре синтаксического дерева.

Например, синтаксически корректная программа может содержать обращение к необъявленной переменной, повторное объявление параметра или операцию с несовместимыми типами. Такие ошибки выявляются на этапе семантического анализа

Основные задачи реализации:

- построение и ведение таблиц символов;
- проверка объявлений и областей видимости;
- обнаружение обращений к неопределённым переменным и формулам;
- проверка типов выражений и условий;
- проверка аргументов вызовов функций и формул;
- обнаружение несовместимых типов при присваивании;
- сбор диагностических сообщений;
- формирование аннотированного AST в формате JSON;

Дополнительно реализован : **автоматический вывод типа локальной переменной по первому корректному присваиванию**.

## 2. Возможности

### 2.1. Таблицы символов и области видимости

Для хранения информации об именах используется таблица символов. Она содержит сведения о переменных, функциях и формулах.

Для символов учитываются:
- имя;
- категория символа;
- тип;
- типы параметров;
- типы возвращаемых значений функций;
- признак того, что тип переменной был выведен автоматически.

Поддерживаются вложенные области видимости. При поиске символа анализатор проверяет текущую область, а затем при необходимости переходит к родительским областям.

Это позволяет находить доступные переменные и отличать локальные объявления от символов, определённых во внешних областях.

### 2.2. Проверка объявлений

Анализатор проверяет корректность использования объявленных символов.

В частности, обнаруживаются:
- повторные объявления параметров;
- повторные объявления функций и формул;
- обращения к неопределённым переменным;
- обращения к неопределённым формулам;
- попытки присваивания значения символу, который не является переменной.

При обработке ошибок анализатор по возможности продолжает проверку оставшейся части программы, чтобы сообщить о нескольких проблемах за один запуск.

### 2.3. Проверка типов


В текущей реализации представлены следующие основные типы:

| Тип | Обозначение | Описание |
|---|---|---|
| Целое число | `int` | Целочисленные значения |
| Массив целых чисел | `int[]` | Массив целых чисел |
| Логическое значение | `bool` | Результат логических операций и сравнений |

Внутри анализатора также используются специальные состояния:

- `<unknown>` — тип пока неизвестен;
- `<invalid>` — выражение содержит семантическую ошибку или не может быть корректно типизировано.


### 2.4. Проверка выражений и условий

Анализатор проверяет типы операндов и ограничения поддерживаемых операций.

В частности, проверяется:
- совместимость типов операндов сравнений;
- использование целочисленных операндов в упорядочивающих сравнениях;
- использование логических выражений в логических операциях;
- корректность логического отрицания;
- типы индексов массивов;
- совместимость типа присваиваемого значения с типом элемента массива.

Если обнаруживается несовместимость, анализатор формирует диагностическое сообщение.

Например, попытка использовать логическое значение там, где требуется целое число, может привести к сообщению о несовместимых типах.

### 2.5. Проверка функций и формул

При работе с вызовами функций и формул анализатор проверяет:
- существование вызываемого символа;
- соответствие категории символа выполняемой операции;
- количество переданных аргументов;
- совместимость типов аргументов с типами соответствующих параметров.

### 2.6. Вывод типа локальной переменной

Если локальная переменная впервые встречается в качестве цели присваивания и ранее не была объявлена в доступных областях, анализатор создаёт для неё запись в таблице символов.

Если присваиваемое выражение имеет известный корректный тип, этот тип становится типом переменной.

Например:

```funny
calculate(a: int)
returns result: int
{
    x = a + 1;
    result = x;
}
```

В выражении `a + 1` оба операнда имеют тип `int`, поэтому результат также имеет тип `int`. Следовательно, переменной `x` присваивается выведенный тип `int`.

При последующих присваиваниях анализатор использует сохранённый тип и проверяет совместимость нового значения с ним.

Если переменной `x` уже выведен тип `int`, присваивание ей логического значения должно приводить к ошибке:

```funny
positive(a: int) => a > 0

calculate(a: int)
returns result: int
{
    x = a + 1;
    x = positive(a);
    result = x;
}
```

Здесь `a + 1` имеет тип `int`, а вызов `positive(a)` возвращает логическое значение `bool`. Поэтому второе присваивание несовместимо с выведенным типом `x`.

Если первое присваивание содержит ошибочное выражение и его тип неизвестен, анализатор не должен считать этот тип корректно выведенным. Последующее корректное присваивание может позволить определить тип переменной.

## 3. Структура проекта

Основные компоненты, относящиеся к семантическому анализу:

```text
funny-lexer/
├── cmd/
│   ├── lexer/
│   ├── parser/
│   └── semantic/
├── internal/
│   ├── ast/
│   ├── dfa/
│   ├── nfa/
│   ├── parser/
│   ├── runner/
│   ├── semantic/
│   └── spec/
├── examples/
├── tests/
├── go.mod
└── README.md
```

Назначение основных компонентов:

| Компонент | Назначение |
|---|---|
| `cmd/semantic` | Точка входа для запуска семантического анализатора |
| `internal/ast` | Структуры узлов абстрактного синтаксического дерева |
| `internal/parser` | Синтаксический анализ исходного текста |
| `internal/semantic/analyzer.go` | Организация семантического анализа |
| `internal/semantic/expressions.go` | Проверка выражений и определение их типов |
| `internal/semantic/statements.go` | Проверка операторов и присваиваний |
| `internal/semantic/symbols.go` | Символы, таблицы символов и области видимости |
| `internal/semantic/types.go` | Представление типов и проверка совместимости |
| `internal/semantic/annotated_json.go` | Формирование аннотированного AST в JSON |
| `internal/semantic/analyzer_test.go` | Модульные тесты семантического анализатора |
| `tests/` | Дополнительные тесты проекта |

## 4. Требования

Для сборки и запуска необходимы:

- установленный Go;
- исходный код проекта;
- терминал, открытый в корневом каталоге репозитория.

Проверить установленную версию Go:

```bash
go version
```

Перейти в каталог проекта:

```bash
cd ~/nsu/verif_transl/funny-lexer
```

## 5. Сборка и запуск

### 5.1. Запуск без предварительной сборки

Для запуска семантического анализатора на исходном файле Funny используется команда:

```bash
go run ./cmd/semantic path/to/program.fun
```

Вместо `path/to/program.fun` необходимо указать путь к исходному файлу.

Например, если программа находится в `examples/program.fun`:

```bash
go run ./cmd/semantic examples/program.fun
```

Имя `program.fun` в примерах является условным: указывайте реально существующий файл.

### 5.2. Сборка исполняемого файла

Собрать анализатор можно командой:

```bash
go build -o semantic ./cmd/semantic
```

Запуск:

```bash
./semantic path/to/program.fun
```

### 5.3. Проверка сборки всех пакетов

Чтобы проверить, что проект компилируется целиком:

```bash
go build ./...
```

Команда собирает пакеты проекта. Она не заменяет запуск семантического анализатора на конкретной программе и не заменяет автоматические тесты.

## 6. Формат входных данных

На вход подаётся исходный код на языке Funny, поддерживаемом используемым парсером.

Пример программы:

```funny
positive(x: int) => x > 0

calculate(a: int)
returns result: int
{
    x = a + 1;
    result = x;
}
```

В этом примере:
- `positive` — формула, возвращающая логический результат сравнения;
- `calculate` — функция с целочисленным параметром `a`;
- `x` — локальная переменная, тип которой выводится из выражения `a + 1`;
- `result` — переменная, указанная в объявлении возвращаемого значения.

Пример демонстрирует работу с конструкциями, поддерживаемыми текущей реализацией. Он не означает, что анализатор поддерживает все возможные конструкции языка Funny.
